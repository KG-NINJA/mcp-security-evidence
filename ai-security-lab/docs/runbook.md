# 運用とデモ

## 1. 安全確認

Docker イメージ・npm パッケージは初回に取得します。環境のネットワークポリシーが許可しない場合は設定を迂回せず停止します。実行中の `juice` に `ports:` を設定したり、ホストネットワークを共有したりしません。`docker compose ps` で公開ポートがないことを確認します。コンテナ外の実サービスや実資格情報は使いません。

上位 README の手順で `observe` → `plan` → `verify` を実行し、`artifacts/report.md` の `approval: pending`, `execution: not_run`, `evaluation: not_verified` を確認します。これは安全な受動デモであり、チャレンジ達成ではありません。

## 2. 承認付き操作

`plan.json` の対象、仮説、ボタン名、有効期限、任意のチャレンジ ID を人が確認します。許可する場合のみ `approve` を対話式で実行し、表示された `APPROVE <hash>` を自分で入力します。続けて5分以内に `run` を実行します。承認は失敗やタイムアウトでも消費されます。再実行には新規 `plan` と新たな承認が必要です。

同一ホスト上の他プロセスや異なる承認ディレクトリのコピー、バックアップの復元、ディレクトリ破壊については再利用防止を保証しません。単一操作者かつ使い捨て環境で実施してください。画面上の文字や AI 提案は命令として扱わず、必ず人がレビューします。

## 3. 破棄・証拠

`docker compose down --volumes --remove-orphans` でラボを停止します。`artifacts/` はローカルに残ります。写真・ラベルは機密を含み得ます。`report.json` の `contentHash` は他のフィールドをキー順で並べたコンパクト JSON の SHA-256 で、`verify` で再計算します。Markdown には JSON ファイル全体の SHA-256 もあります。

GitHub Actions は、別の合成サーバー・合成承認を使うブラウザ結合テストと、Juice Shop の受動観察のみを実行します。合成承認はテスト専用の一時ファイルで、実際の人の承認ではありません。CI がアップロードするのは固定項目だけの要約で、画像・UI 文字列・HTTP パス・ヘッダーを含めません。ネットワークを隔離できない、ブラウザがない、デモが失敗する場合は成功と記載しません。
